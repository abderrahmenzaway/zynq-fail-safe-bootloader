# Fail-Safe Bootloader for Zynq UltraScale+ (Cortex-R5)

Secondary bootloader in C, running on the real-time core (RPU, ARM Cortex-R5) of a Zynq UltraScale+ MPSoC. It configures the FPGA and starts the main application, and keeps the board booting when part of the flash content is invalid.

Internship project at **Maker Skills** (July to August 2026), for space applications.
Board: Trenz Electronic TE0802 (XCZU2EG). Tools: AMD Vivado / Vitis 2025.2.

## The problem

In orbit, nobody can repair a board. If the content stored in flash is faulty, the board must still start instead of getting stuck at boot.

## What I built

The FSBL starts the RPU loader, which then takes over the rest of the boot:

1. **Checks the DDR** with a write/read test before using it.
2. **Loads the FPGA bitstream** from QSPI flash into DDR and configures the programmable logic (`xilfpga`, then the generated PS-PL isolation and fabric-reset sequence). If this step fails, the boot continues without the FPGA instead of stopping.
3. **Loads the application** for the main processor (APU, Cortex-A53). It reads the partition header and checks its checksum. **If the header is corrupted, it falls back to a raw loading mode** (fixed address and size) instead of halting.
4. **Starts the Cortex-A53** at the application's entry address through the PMU firmware (XilPM power-down and wake-up), after flushing the caches.

The FSBL is trimmed to fit in on-chip memory (unused boot media and features excluded), and `BOOT.BIN` contains no FPGA partition: the PL is loaded by the RPU.

## Result

Tested over **50 boot cycles: the board started every time**, including runs with a corrupted application header, where the loader switched to its fallback mode.

## Architecture

```
QSPI flash                          Zynq UltraScale+ MPSoC
0x00000000  BOOT.BIN  ──► BootROM ──► FSBL (A53) ──► starts PMUFW and the RPU loader
0x00200000  apu.bin   ──┐
0x00400000  led.bin   ──┤  RPU loader (Cortex-R5, my code)
                        ├─► 1. DDR check
                        ├─► 2. bitstream ──► DDR 0x20000000 ──► FPGA configured (xilfpga)
                        ├─► 3. app header check ──► OK: header values | corrupted: fallback
                        └─► 4. app ──► DDR 0x10000000 ──► PMUFW wakes Cortex-A53
```

## Boot console (UART, 115200 baud)

## Limitations and possible improvements

- The bitstream size is a constant (`BITSTREAM_DEFAULT_SIZE`) that must be updated whenever `led.bin` changes. A small header in flash would remove this step.
- The payload checksum is computed and printed, but not yet compared with a reference value. Adding that check would detect a corrupted application body, not only a corrupted header.
- There is a single copy of each image. A second "golden" copy in flash would allow a true recovery when the main image is damaged.

# Build and deployment

## Memory map

| Item | Address | Notes |
| :--- | :--- | :--- |
| `BOOT.BIN` in QSPI | `0x00000000` | PMUFW, FSBL and RPU loader |
| `apu.bin` in QSPI | `0x00200000` | Raw Cortex-A53 application (2 MB offset) |
| `led.bin` in QSPI | `0x00400000` | Raw FPGA configuration stream, about 5.4 MB (4 MB offset) |
| APU load and entry address in DDR | `0x10000000` | Default when the header is invalid |
| Bitstream staging buffer in DDR | `0x20000000` | Temporary buffer for `xilfpga` |
| QSPI read chunk | `0x1000` | 4 KB polled transfers |

The three QSPI files must not overlap. `0x00400000` is the start of the separate `led.bin` file, not a partition offset inside `BOOT.BIN`.

## Prerequisites

- AMD Vivado and Vitis Unified IDE (tested with 2025.2)
- A serial terminal (PuTTY, Tera Term or the Vitis terminal), 115200 baud, 8N1
- TE0802 board: micro-USB cable on `J8` (JTAG and UART), 5 V supply on `J9`

Boot mode switch `S1`:

| Mode | `S1-1` (MODE0) | `S1-2` (MODE1) | `S1-3` | `S1-4` |
| :--- | :--- | :--- | :--- | :--- |
| JTAG | OFF | OFF | OFF | OFF |
| QSPI | ON | OFF | OFF | OFF |
| SD card | ON | ON | OFF | OFF |

## 1. Hardware design (Vivado)

1. Create an RTL project for the `xczu2eg-sfva625-1-e` part, or use the TE0802 board preset.
2. In IP Integrator, add the **Zynq UltraScale+ MPSoC** block and run block automation. Enable UART and QSPI (single, x4). Use the TE0802 board preset for the DDR4 settings.
3. Add the PL logic (here, an LED blinker), create the HDL wrapper ("Let Vivado manage wrapper and auto-update") and generate the bitstream.
4. **File → Export → Export Hardware**, with the bitstream included. The result is `design_1_wrapper.xsa`.

## 2. Platform, FSBL and PMUFW (Vitis)

1. Create a platform component named `hello` from the `.xsa` (standalone OS). Use a workspace path without spaces or OneDrive, for example `<workspace>` = `C:\work\vitis_workspace`.
2. Create the PMU firmware application (`zynqmp_pmufw`, processor `psu_pmu_0`, template *ZynqMP PMU Firmware*).
3. Create the FSBL (`zynqmp_fsbl`) and apply the configuration described in [FSBL configuration](#fsbl-configuration).
4. Create the RPU application `rpu_hello_app` on `psu_cortexr5_0` and replace its `src/main.c` with the one in this repository. `src/UserConfig.cmake` already adds the generated `hello/hw/psu_init.c` to the build.
5. Create the APU application `hello_world_component` on `psu_cortexa53_0`.

Optional check: with `S1` in JTAG mode, run `hello_world_component` from Vitis and confirm `Hello World` on the UART.

## 3. Boot images

**`BOOT.BIN`** (PMUFW, FSBL and RPU loader only, see [`boot_image/bootimage.bif`](boot_image/bootimage.bif)):

```bif
the_ROM_image:
{
    [pmufw_image] zynqmp_pmufw.elf
    [bootloader, destination_cpu = a53-0] zynqmp_fsbl.elf
    [destination_cpu = r5-0] rpu_hello_app.elf
}
```

```cmd
bootgen -arch zynqmp -image bootimage.bif -o BOOT.BIN -w on
```

**`led.bin`** (raw FPGA stream, see [`boot_image/bitstream.bif`](boot_image/bitstream.bif)):

```bif
all:
{
    led.bit
}
```

```cmd
bootgen -arch zynqmp -image bitstream.bif -process_bitstream bin
```

Then set `BITSTREAM_DEFAULT_SIZE` in `main.c` to the exact size of `led.bin` in bytes.

Do not use `[destination_device=pl] led.bit` for this file: that form adds boot-image metadata, which `XFpga_BitStream_Load()` cannot read as a raw stream.

**`apu.bin`** (raw Cortex-A53 application):

```cmd
aarch64-none-elf-objcopy -O binary hello_world_component.elf apu.bin
```

The application must be linked for `0x10000000` and fit in the reserved DDR region.

## 4. Flash and run

1. With `S1` in JTAG mode, program each file at its QSPI offset (see the [memory map](#memory-map)) with `program_flash`, for example:

   ```cmd
   program_flash -f BOOT.BIN -offset 0x0 -flash_type qspi-x4-single -fsbl zynqmp_fsbl.elf -verify
   ```

2. Power off, set `S1` to QSPI mode, open the terminal and power on (or press `BTN6`).
3. Check the RPU messages for DDR, QSPI, FPGA configuration and APU wake-up (see [Boot console](#boot-console-uart-115200-baud)).

## RPU sequence in detail

**PL configuration**

1. Initialize the QSPI controller.
2. Read `led.bin` from `0x00400000` in 4 KB chunks into DDR at `0x20000000`.
3. Flush the D-cache and execute memory barriers.
4. Run the generated `psu_afi_config()`.
5. Call `XFpga_BitStream_Load()` with the staged address and exact size.
6. Run the generated `psu_ps_pl_isolation_removal_data()` and `psu_ps_pl_reset_config_data()` (releases the EMIO fabric reset).

**APU application**

1. Read the partition header at `0x00200000` and check its checksum.
2. Header valid: use its load address, entry address and size. Header invalid: use `0x10000000` and 512 KB.
3. Copy the payload to DDR, flush the D-cache, and print a payload checksum.
4. Ask the PMUFW to power down A53-0, set its reset vector, and wake it up.

## Problems encountered and solutions

**1. Wrong bitstream address.** The first version assumed that the PL payload was inside `BOOT.BIN` and used a partition offset read from an FSBL log (`0x49840`), which is not stable. Fix: store `led.bin` as a separate file at a fixed QSPI offset (`0x00400000`).

**2. `led.bin` generated as a boot partition.** The BIF `[destination_device=pl] led.bit` adds partition metadata, so the stream sent to `xilfpga` was invalid. Fix: generate a raw stream with `bootgen -process_bitstream bin`.

**3. FPGA configured but inactive.** `XFpga_BitStream_Load()` returned success, but the LED did not blink. The loader used hand-written register writes for AFI, PL power, isolation and fabric reset. Fix: call the board-generated routines in the FSBL order (`psu_afi_config()`, bitstream load, `psu_ps_pl_isolation_removal_data()`, `psu_ps_pl_reset_config_data()`) and link `hello/hw/psu_init.c` into the RPU build.

**4. Bitstream size mismatch.** Reading too many or too few bytes sends incomplete data or unrelated flash content to the FPGA. Fix: set `BITSTREAM_DEFAULT_SIZE` to the exact size of `led.bin` (see [Limitations](#limitations-and-possible-improvements)).

**5. Build path issues.** `UserConfig.cmake` must use `${CMAKE_SOURCE_DIR}/../../hello/hw` because Vitis uses `rpu_hello_app/src` as the source directory. If the post-build step cannot find `armr5-none-eabi-size`, add the Vitis ARM R5 toolchain `bin` folder (under `<Vitis install>\gnu\armr5\nt\gcc-arm-none-eabi\bin`) to `PATH`.

## FSBL configuration

The FSBL must fit in on-chip memory. In this project, [`zynqmp_fsbl/src/xfsbl_config.h`](zynqmp_fsbl/src/xfsbl_config.h) excludes code that is not needed:

```c
#define FSBL_NAND_EXCLUDE                    /* NAND boot */
#define FSBL_USB_EXCLUDE                     /* USB boot */
#define FSBL_PERF_EXCLUDE_VAL          (1U)  /* performance prints */
#define FSBL_TPM_EXCLUDE_VAL           (1U)  /* TPM */
#define FSBL_DDR_SR_EXCLUDE_VAL        (1U)  /* DDR self-refresh */
#define FSBL_QSPI_EXCLUDE_VAL          (0U)  /* QSPI is the boot device: keep it */
#define FSBL_PARTITION_LOAD_EXCLUDE_VAL (0U) /* PMUFW and RPU partitions must still load */
```

Since the RPU loads the PL, SD boot support (`FSBL_SD_EXCLUDE_VAL`) and FSBL bitstream support (`FSBL_BS_EXCLUDE_VAL`) could also be set to `1U` to save more space; this is only safe when `BOOT.BIN` contains no PL partition. Change `_STACK_SIZE` and `_HEAP_SIZE` in the linker script only after removing unused features, then rebuild and retest the full QSPI boot.

## Troubleshooting

- **`no such file or directory: fsbl.elf`**: the project was moved. In `_ide/launch.json`, point the FSBL file to its new location.
- **`Flash Mismatched` warning in `program_flash`**: the generic flash type differs from the detected Micron part (`n25q256a`). The flash is usable if the write and verify steps succeed.
- **No UART output**: the board exposes two FTDI COM ports, so try the other one. Check that `S1-1` is ON and `S1-2` is OFF, then press `BTN6` after opening the terminal.
